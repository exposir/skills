# 拆工单

把一个计划、规格或对话拆成一组**工单**：曳光弹式垂直切片，每张工单声明**阻塞**它的那些工单。

issue tracker 和分类标签词汇应该已经提供给你了。如果没有，让用户运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

基于对话上下文里已有的东西工作。如果用户传了引用（规格路径、issue 编号或 URL）作为参数，取来读全文和评论。

### 2. 探索代码库（可选）

如果还没探索过代码库，先探索，理解代码的当前状态。工单标题和描述应使用项目的领域词汇表，并尊重你所触及区域的 ADR。

寻找预重构代码的机会，让实现更容易。"先把变化变容易，再做容易的变化。"

### 3. 草拟垂直切片

把工作拆成**曳光弹**工单。

<vertical-slice-rules>

- 每个切片切出一条窄但**完整**的路径，贯穿每一层（schema、API、UI、测试）：垂直，而不是只切一层的水平切片
- 一个完成的切片能独立演示或验证
- 每个切片的大小要能装进一个全新的上下文窗口
- 任何预重构应先做

</vertical-slice-rules>

给每张工单标出**阻塞边**：必须在它开始之前完成的其他工单。没有阻塞项的工单可以立即开始。

**大范围重构是垂直切片的例外。** 一个**大范围重构**（wide refactor）是一个机械性变更（改一个列名、重定义一个共享符号），它的**爆炸半径**波及整个代码库，一次编辑会同时打破上千个调用点，任何垂直切片都无法绿着落地。不要把它硬塞进曳光弹；按**扩张到收缩**（expand–contract）来排序。先扩张：在旧形式旁边加新形式，什么都不破坏。然后按爆炸半径分批迁移调用点（按包、按目录），每批一张工单，被扩张工单阻塞，因为旧形式还在，批与批之间 CI 保持绿色。最后收缩：没有调用者之后再删旧形式，一张被所有迁移批阻塞的工单。当连各批都无法单独保持绿色时，保留这个顺序，但让它们共享一个集成分支，所有批都阻塞一张最终的集成验证工单；只有那里才承诺绿色。

### 4. 向用户提问

把提议的拆分以编号列表呈现。每张工单展示：

- **标题**：简短描述性名称
- **被谁阻塞**：哪些其他工单（如果有）必须先完成
- **它交付什么**：这张工单让什么端到端行为可用

问用户：

- 粒度合适吗？（太粗 / 太细）
- 阻塞边对吗：每张工单是否只依赖真正卡住它的工单？
- 哪些工单该合并或进一步拆分？

反复迭代直到用户批准拆分。

### 5. 把工单发布到已配置的 tracker

发布批准的工单。**怎么发**取决于 `/setup-matt-pocock-skills` 配置的 tracker；工单本身两种方式都一样，只是阻塞边的形态不同：

- **本地文件** → 在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 下每张工单一个文件，按依赖顺序（阻塞者在前）从 `01` 编号。每个文件的"Blocked by"列出它所依赖的编号/标题。用下面的单工单文件模板：一工单一文件，绝不用单个合并文件。
- **真实 issue tracker（GitHub、Linear 等）** → 按依赖顺序（阻塞者在前）每张工单发一个 issue，这样每张工单的阻塞边能引用真实标识符。平台有原生阻塞/子 issue 关系的就用；否则把每张工单的"Blocked by"设为阻塞它的 issue。除非另有指示，打上 `ready-for-agent` 分类标签；这些工单按构造就是 agent 可领取的。

推进**前沿**：阻塞项全部完成的任何工单。对纯线性链来说，就是从上到下。

**不要**关闭或修改任何父 issue。

两种形式都要避免具体文件路径或代码片段：它们很快过时。例外：如果原型产出的一段代码比文字更精确地编码了一个决策（状态机、reducer、schema、类型形状），把它内联进去，并简要注明它来自原型。裁剪到富含决策的部分，不是可运行的演示，只保留重要部分。
