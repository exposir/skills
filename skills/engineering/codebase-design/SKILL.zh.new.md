# 代码库设计

设计**深模块**：大量行为藏在小接口后面，放在干净的接缝处，通过接口就能测。无论在哪设计或重构代码，都用这套语言和原则。目标是：调用方撬动更多行为，维护者修一处就到处修好，测试自然、不费力。

## 术语表

这些词照这个用，别换："组件"、"服务"、"API"、"边界"统统别用。一致的语言才是全部。

**模块（Module）**：有接口有实现的东西。故意不限制大小：一个函数、类、包、跨层切片都算。*别用*：单元、组件、服务。

**接口（Interface）**：调用方要正确使用模块必须知道的所有事情：类型签名，但也包括不变量、调用顺序、错误模式、需要的配置、性能特征。*别用*：API、签名（太窄，只指类型层面）。

**实现（Implementation）**：模块里面的东西，代码体。和**适配器（Adapter）**区分开：一个东西可以小适配器 + 大实现（Postgres 仓库），也可以大适配器 + 小实现（内存假数据）。聊接缝的时候用"适配器"，其他时候用"实现"。

**深度（Depth）**：接口处的杠杆。调用方（或测试）每学一单位接口，能撬动多少行为。接口很小、背后行为很多，模块就**深**；接口几乎和实现一样复杂，模块就**浅**。

**接缝（Seam）**（Michael Feathers）：一个你可以改变行为、但不需要编辑那个位置的地方；模块接口所在的*位置*。接缝放哪本身就是一个设计决策，和接缝后面放什么不是一回事。*别用*：边界（跟 DDD 的限界上下文撞了）。

**适配器（Adapter）**：一个接缝处满足接口的具体东西。说的是*角色*（填什么槽），不是里面是什么。

**杠杆（Leverage）**：调用方从深度里拿到的。每学一单位接口，拿回更多能力。一个实现，回馈 N 个调用点和 M 个测试。

**局部性（Locality）**：维护者从深度里拿到的。变更、bug、知识、验证全挤在一个地方，不散到各个调用方。修一次，全修好。

## 深 vs 浅

**深模块** = 小接口 + 大实现：

```
┌─────────────────────┐
│     小接口          │  ← 少数方法，简单参数
├─────────────────────┤
│                     │
│    深度实现         │  ← 复杂逻辑全藏里面
│                     │
└─────────────────────┘
```

**浅模块** = 大接口 + 薄实现（别写这样的）：

```
┌─────────────────────────────────┐
│           大接口                │  ← 一堆方法，复杂参数
├─────────────────────────────────┤
│  薄实现                         │  ← 就转个手
└─────────────────────────────────┘
```

设计接口时问三句：

- 方法数能减吗？
- 参数能简化吗？
- 更复杂的东西能塞进里面吗？

## 原则

- **深度是接口的属性，不是实现的。** 深模块里面可以由小型的、可 mock 的、可换的部件拼成；它们只是不属于接口。模块可以有**内部接缝**（对其实现私有，自己测试用），外加接口处的**外部接缝**。
- **删除测试。** 想象删掉这个模块。复杂度消失了？它就是个过手货。复杂度重新出现在 N 个调用方？它挣到了自己的位置。
- **接口就是测试面。** 调用方和测试走同一个接缝。你想测到接口*后面*去，说明模块形状可能不对。
- **一个适配器 = 假接缝，两个 = 真接缝。** 除非确实有东西在这个接缝上变化，别引入它。

## 为可测试性做设计

好接口让测试自然：

1. **接受依赖，别在内部创建。**

   ```typescript
   // 可测试
   function processOrder(order, paymentGateway) {}

   // 难测试
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，别搞副作用。**

   ```typescript
   // 可测试
   function calculateDiscount(cart): Discount {}

   // 难测试
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **小表面积。** 方法少 = 测试少。参数少 = 测试好写。

## 关系

- 一个**模块**有且仅有一个**接口**（呈现给调用方和测试的表面）。
- **深度**是**模块**的属性，对着**接口**量。
- **接缝**是**模块**的**接口**在的地方。
- 一个**适配器**坐在**接缝**处，满足**接口**。
- **深度**给调用方**杠杆**，给维护者**局部性**。

## 被毙掉的框架

- **深度 = 实现行数 / 接口行数**（Ousterhout）：奖励堆代码。我们改用深度即杠杆。
- **"接口" = TypeScript 的 `interface` 关键字**：太窄，这里的接口包括调用方必须知道的每个事实。
- **"边界"**：跟 DDD 撞了。说**接缝**或**接口**。
