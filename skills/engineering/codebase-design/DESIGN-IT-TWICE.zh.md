# 设计两次

当用户想为一个选定的深化候选探索替代接口时，使用这个并行子代理模式。基于"设计两次"（Ousterhout）：你的第一个想法不太可能是最好的。

使用 [SKILL.zh.md](SKILL.zh.md) 中的词汇：**模块**、**接口**、**接缝**、**适配器**、**杠杆**。

## 流程

### 1. 框定问题空间

在启动子代理之前，为选定的候选写一个面向用户的问题空间说明：

- 任何新接口需要满足的约束
- 它将依赖的依赖项，以及它们属于哪个类别（见 [DEEPENING.zh.md](DEEPENING.zh.md)）
- 一个粗略的示意性代码草图，用来把约束落到实处，不是提案，只是让约束变得具体的方式

把这展示给用户，然后立即进入步骤 2。用户在子代理并行工作时阅读和思考。

### 2. 启动子代理

并行启动 3 个以上子代理。每个必须为深化模块产出**截然不同**的接口。

给每个子代理一个独立的技术简报（文件路径、耦合细节、来自 [DEEPENING.zh.md](DEEPENING.zh.md) 的依赖类别、接缝后面放什么）。简报独立于步骤 1 中面向用户的问题空间说明。给每个 agent 不同的设计约束：

- Agent 1："最大化接口最小化：目标是最多 1 到 3 个入口点。最大化每个入口点的杠杆。"
- Agent 2："最大化灵活性：支持多种用例和扩展。"
- Agent 3："为最常见的调用方优化：让默认情况变得简单。"
- Agent 4（如果适用）："围绕端口与适配器设计跨接缝依赖。"

在简报中同时包含 [SKILL.zh.md](SKILL.zh.md) 词汇和 CONTEXT.md 词汇，这样每个子代理都能用架构语言和项目的领域语言一致地命名东西。

每个子代理输出：

1. 接口（类型、方法、参数，加上不变量、顺序、错误模式）
2. 使用示例，展示调用方如何使用它
3. 实现藏在接缝后面的东西
4. 依赖策略和适配器（见 [DEEPENING.zh.md](DEEPENING.zh.md)）
5. 权衡：杠杆在哪里高，在哪里薄

### 3. 呈现和比较

按顺序呈现设计，让用户能逐个吸收，然后以文字比较它们。按**深度**（接口处的杠杆）、**局部性**（变更集中在哪里）和**接缝位置**来对比。

比较之后，给出你自己的推荐：你认为哪个设计最强，以及为什么。如果不同设计的元素组合起来会很好，提出一个混合方案。要有主见：用户想要的是一个有力的解读，不是菜单。
