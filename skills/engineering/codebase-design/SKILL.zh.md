# 代码库设计

设计**深度模块**：大量行为藏在小接口后面，放在干净的接缝处，通过该接口可测试。在任何代码被设计或重构的地方使用这套语言和原则。目标是对调用方来说是杠杆，对维护者来说是局部性，对所有人来说是可测试性。

## 术语表

精确使用这些术语：不要用"组件"、"服务"、"API"或"边界"来替代。一致的语言是全部意义。

**模块（Module）**：任何有接口和实现的东西。刻意不限定尺度：一个函数、类、包或跨层切片。*避免用*：单元、组件、服务。

**接口（Interface）**：调用方要正确使用模块所必须知道的一切：类型签名，也包括不变量、顺序约束、错误模式、所需配置和性能特征。*避免用*：API、签名（太窄，只指类型层面的表面）。

**实现（Implementation）**：模块内部的东西，它的代码体。区别于**适配器（Adapter）**：一个东西可以是一个小适配器带着大实现（Postgres 仓库），也可以是一个大适配器带着小实现（内存假数据）。当话题是接缝时用"适配器"，否则用"实现"。

**深度（Depth）**：接口处的杠杆。调用方（或测试）每学习一单位接口能行使多少行为。当大量行为藏在很小接口后面时，模块是**深的**；当接口几乎和实现一样复杂时，模块是**浅的**。

**接缝（Seam）**（Michael Feathers）：一个你可以改变行为而不需要编辑那个地方的位置；一个模块接口所在的*位置*。把接缝放在哪本身就是一个设计决策，与接缝后面放什么不同。*避免用*：边界（与 DDD 的限界上下文过载）。

**适配器（Adapter）**：一个满足接缝处接口的具体东西。描述的是*角色*（它填什么槽），不是实质（它里面是什么）。

**杠杆（Leverage）**：调用方从深度中获得的东西。每学习一单位接口获得更多能力。一个实现回馈 N 个调用点和 M 个测试。

**局部性（Locality）**：维护者从深度中获得的东西。变更、bug、知识和验证集中在一个地方，而不是分散到各个调用方。修一次，到处修好。

## 深 vs 浅

**深模块** = 小接口 + 大量实现：

```
┌─────────────────────┐
│     小接口          │  ← 少数方法，简单参数
├─────────────────────┤
│                     │
│    深度实现         │  ← 复杂逻辑藏在里面
│                     │
└─────────────────────┘
```

**浅模块** = 大接口 + 少量实现（避免）：

```
┌─────────────────────────────────┐
│           大接口                │  ← 很多方法，复杂参数
├─────────────────────────────────┤
│  薄实现                         │  ← 只是转手
└─────────────────────────────────┘
```

设计接口时问自己：

- 我能减少方法数量吗？
- 我能简化参数吗？
- 我能把更多复杂度藏进里面吗？

## 原则

- **深度是接口的属性，不是实现的属性。** 一个深模块内部可以由小型的、可 mock 的、可替换的部件组成；它们只是不属于接口。一个模块可以有**内部接缝**（对其实现私有，由它自己的测试使用），也可以有接口处的**外部接缝**。
- **删除测试。** 想象删除这个模块。如果复杂度消失了，它就是个过手模块。如果复杂度重新出现在 N 个调用方那里，它就在挣自己的位置。
- **接口就是测试面。** 调用方和测试跨同一个接缝。如果你想要测到接口*后面*去，模块的形状可能错了。
- **一个适配器意味着假设的接缝。两个适配器意味着真实的接缝。** 除非确实有东西在这个接缝上变化，否则不要引入接缝。

## 为可测试性而设计

好的接口让测试变得自然：

1. **接受依赖，不要创建依赖。**

   ```typescript
   // 可测试
   function processOrder(order, paymentGateway) {}

   // 难测试
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，不要产生副作用。**

   ```typescript
   // 可测试
   function calculateDiscount(cart): Discount {}

   // 难测试
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **小表面积。** 更少方法 = 需要更少测试。更少参数 = 更简单的测试设置。

## 关系

- 一个**模块**有且只有一个**接口**（它呈现给调用方和测试的表面）。
- **深度**是**模块**的属性，相对其**接口**来衡量。
- **接缝**是**模块**的**接口**所在的位置。
- 一个**适配器**坐在**接缝**处，满足**接口**。
- **深度**为调用方产生**杠杆**，为维护者产生**局部性**。

## 被拒绝的框架

- **深度作为实现行数与接口行数的比值**（Ousterhout）：奖励堆砌实现。我们改用深度即杠杆。
- **"接口"即 TypeScript 的 `interface` 关键字或类的公有方法**：太窄：这里的接口包括调用方必须知道的每个事实。
- **"边界"**：与 DDD 的限界上下文过载。用**接缝**或**接口**。
