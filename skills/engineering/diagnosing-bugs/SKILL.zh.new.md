# 诊断 Bug

这是一套诊断疑难 bug 的固定流程。没有明确的正当理由，不要跳过任何阶段。

核心原则：**先建立一条能自动"变红"的检查命令，让 bug 直接暴露出来；命令建立之前，不允许开始猜测。**

开始之前，先读一下代码库里的 `CONTEXT.md`（如果有的话），对相关模块建立清晰的认识；再看一眼你要修改的那块区域的架构决策记录（Architecture Decision Record，简称 ADR）。

## 先脱敏

这个流程会要求你展示命令、输出和抓取到的数据。**所有密钥一律先脱敏**：写成 `<REDACTED>`。命令尽量基于环境变量构建，使凭证留在环境中，而不是出现在你展示的内容里。抓取到的数据包含认证头：只引用携带信号的行。

如果脱敏之后信息不足以诊断，直接说明，并向用户请求。

## 第一步：建立一条能变红的回路

**这一步就是全部。** 后面所有阶段都是机械执行。只要你能为这个 bug 建立一条**紧致**的对错信号（一个会因为这个 bug 变红的信号），根因就一定能找到；二分、假设验证、插桩，全都依赖这个信号。没有信号，看再多代码也没有用。

把绝大部分精力花在这一步。**要激进。要有创意。不要放弃。**

### 建立回路的方法，按优先级从高到低

1. **写一个会失败的测试**：在能触达 bug 的任何一个层级写测试，单元、集成、端到端都可以。
2. **Curl / HTTP 脚本**：针对运行中的 dev server 直接调用接口。
3. **命令行调用**：使用一个固定的样例输入，把输出与一份已知正确的快照做 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer）：驱动 UI 操作，断言 DOM、console、network。
5. **重放抓取到的数据**：将真实的网络请求、载荷、事件日志保存到磁盘，在隔离环境中原样重放。
6. **搭建一次性最小环境**：启动系统的最小子集（一个服务 + mock 依赖），通过一个函数调用触发 bug 代码路径。
7. **随机输入测试**：如果 bug 表现为"有时输出错误"，运行 1000 个随机输入寻找失败模式。
8. **二分定位**：bug 出现在两个已知状态之间（提交、数据集、版本），将"启动到状态 X、检查、重复"自动化，交给 `git bisect run`。
9. **新旧对比**：同一份输入分别运行旧版本和新版本（或两种配置），diff 输出。
10. **人在回路脚本**：最后的手段。当必须有人手动操作时，用 `scripts/hitl-loop.template.sh` 驱动操作者按步骤执行，回路仍然结构化，捕获的输出反馈给你。

回路建立正确，bug 就相当于修复了 90%。

### 收紧回路

把回路当作产品来打磨。一旦有了回路，继续收紧：

- 能否更快？（缓存初始化、跳过无关的启动步骤、缩小测试范围。）
- 信号能否更锐利？（断言具体症状，而不是"没有崩溃"。）
- 能否更确定？（固定时间、固定随机种子、隔离文件系统、冻结网络。）

30 秒且不稳定的回路，几乎等于没有回路；2 秒且确定性的回路才算紧致，是调试的利器。

### 不稳定的 bug

目标不是干净的复现，而是**提高复现率**。将触发器运行 100 次，并行化，增加压力，收窄时间窗口，注入 sleep。复现率 50% 的 bug 可以调试，1% 的不能，持续提高到可调试为止。

### 确实无法建立回路时

停下来，明确说明。列出你尝试过的方法，然后向用户请求以下三样之一：(a) 复现环境的访问权限；(b) 脱敏后的捕获产物（HAR 文件、日志 dump、core dump、带时间戳的录屏）；(c) 添加临时生产埋点的许可。回路建立之前，**禁止**进入假设阶段。

### 第一步完成的标志

回路**紧致**且**能变红**，具体说：你能说出**一条命令**（脚本路径、测试命令、curl），并且**已经实际运行过至少一次**（展示调用和输出，已脱敏），它满足：

- [ ] **能变红**：经过真实的 bug 代码路径，断言的是**用户描述的那个症状**，因此 bug 存在时它变红，修复后变绿。注意不是"运行不报错"，而是必须能捕获 _这一个具体的 bug_。
- [ ] **稳定**：每次运行结果一致（不稳定的 bug 按上文，固定在足够高的复现率）。
- [ ] **快**：秒级，不是分钟级。
- [ ] **无人值守**：你能独立运行完整流程；需要人参与时仅通过 `scripts/hitl-loop.template.sh`。

如果你发现在这条命令存在之前就开始阅读代码、构建理论，**停下来。跳过信号直接猜测原因，正是这套流程要防止的失败模式。** 没有能变红的命令，就不进入第二步。

## 第二步：复现 + 最小化

运行这条命令，观察它变红。

确认三件事：

- [ ] 变红的是**用户描述的那个失败**，不是旁边碰巧出现的另一个失败。抓错 bug，就会修错地方。
- [ ] 失败能反复出现（不稳定的 bug，复现率高到足以支撑调试）。
- [ ] 记录确切的症状（报错信息、错误输出、耗时），后面验证修复时对照。

### 最小化

变红之后，把场景缩减到**最小但依然变红**。输入、调用方、配置、数据、步骤，每次只删一项，每删一项后重新运行回路，只保留对失败真正必要的部分。

这样做的价值：场景越小，第三步需要怀疑的要素越少，而且这个最小场景就是第五步现成的回归测试。

完成标准：**剩下的每一样都是必要的**，删除任意一项，命令就不再变红。

复现和最小化都完成，才能进入下一步。

## 第三步：列假设

在开始验证之前，先列出 **3 到 5 个按可能性排序的假设**。只列一个假设，会锚定在第一个看似合理的想法上。

每个假设必须**可证伪**：明确陈述它做出的预测。

> 格式："如果 X 是根因，那么改掉 Y 会让 bug 消失 / 改掉 Z 会让它更严重。"

无法陈述预测的假设只是感觉，不是假设：删除它，或打磨到能陈述。

**在开始验证之前，先向用户展示排序后的列表。** 用户往往一句话就能重新排序（"我们刚上线的改动正好是第 3 条"），或者直接告知哪些假设已被排除。这一步成本很低，却能节省大量时间。不要因此阻塞：用户不在时，按你的排序继续。

## 第四步：插桩验证

每一次探测都必须对应第三步中的一条具体预测。**一次只改一个变量。**

工具优先级：

1. **调试器 / 交互式解释器检查**，环境支持时优先使用。交互式解释器（Read-Eval-Print Loop，简称 REPL）是一个"输入一行代码，立刻执行并打印结果"的命令行环境，比如 Node、Python 的交互终端或浏览器 console；调试时直接用它在断点处查看变量和表达式的值，一个断点胜过十条日志。
2. **定向日志**，打在能区分假设的边界处。
3. 绝不"到处打日志再逐个排查"。

**为每条调试日志打上唯一前缀**，比如 `[DEBUG-a4f2]`。收尾时用一条 grep 命令全部清除。无前缀的日志保留，带前缀的全部删除。

**性能问题分支。** 排查性能回归时，日志大多不适用。先建立基线测量（计时脚本、`performance.now()`、profiler、查询计划），再二分定位。先测量，后修复。

## 第五步：修复 + 回归测试

**回归测试写在修复之前**，但前提是存在一个**正确的测试位置**。

什么是正确的位置：测试能以 bug 的**真实发生方式**复现它，即在真实的调用点触发。如果唯一可用的位置太浅（bug 需要多个调用方共同触发，而测试中只有一个调用方；单元测试复现不了触发 bug 的那条调用链），在该位置写回归测试只会带来虚假的信心。

**找不到正确的位置，这本身就是结论。** 记录下来：是代码库的架构使这个 bug 无法被测试锁定。在下一阶段标记这个发现。

如果存在正确的位置：

1. 把最小场景转化为该位置上的失败测试。
2. 观察它失败。
3. 应用修复。
4. 观察它通过。
5. 针对原始（未最小化）场景，重新运行第一步的回路。

## 第六步：清理

在宣布完成之前：

- [ ] 原始场景不再复现（重新运行第一步的回路）
- [ ] 回归测试通过（或已记录"没有正确位置"这一发现）
- [ ] 所有 `[DEBUG-...]` 插桩代码全部移除（`grep` 前缀确认）
- [ ] 一次性原型已删除（或移动到明确标注的调试目录）
- [ ] 在 commit / PR 消息中写明最终被验证为真的假设，让下一位调试者直接获得结论

## 第七步（可选）：同步文档

修复完成后，检查是否存在需要同步的文档（开发文档、bug 记录、变更日志、接口文档等）。如果存在，把这次修复补充进去：

- [ ] **根因**：bug 为什么发生
- [ ] **原因归类**：判断 bug 的来源，是开发阶段写错，还是某次修复引入的新问题；可追溯开发记录（提交历史、PR 等）确认；区分是理解错误、上下文缺失还是其他原因；写明后续开发如何避免同类问题
- [ ] **修复**：改了什么、为什么这样改
- [ ] **验证**：回归测试在哪里、如何运行
- [ ] **遗留事项**：已知限制或后续待办（如果有）
- [ ] **格式规范**：遵循文档本身要求的格式或规范（如果有）

没有相关文档就跳过这一步。
