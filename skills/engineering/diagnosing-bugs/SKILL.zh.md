# 诊断 Bug

一套针对疑难 bug 的纪律性流程。跳过阶段需要明确理由。

探索代码库时，先读 `CONTEXT.md`（如果存在）建立相关模块的清晰心智模型，并检查你触及范围内的 ADR。

## 脱敏

本 skill 会要求你展示命令、输出和捕获产物。**先脱敏所有密钥**：用 `<REDACTED>` 替换。用环境变量构建回路，凭证留在环境里而非展示内容中。捕获产物携带认证头：只引用承载信号的那些行。

如果脱敏后输出不足以诊断 bug，明说并询问用户。

## 阶段一：构建反馈回路

**这是本 skill 的核心。** 其余都是机械操作。如果你有一个**紧致**的 pass/fail 信号（一个会在 _这个_ bug 上变红的信号），你就能找到根因；二分法、假设验证、插桩都只是消费这个信号。没有它，看再多代码也救不了你。

在这里投入不成比例的努力。**要激进。要创意。拒绝放弃。**

### 构建方式，大致按优先级

1. **失败测试**，在能触及 bug 的任意接缝处：单元、集成、端到端。
2. **Curl / HTTP 脚本**，针对运行中的 dev server。
3. **CLI 调用**，用固件输入，stdout 与已知正确的快照做 diff。
4. **Headless 浏览器脚本**（Playwright / Puppeteer），驱动 UI 并对 DOM/console/network 做断言。
5. **回放捕获的 trace。** 把真实的网络请求/载荷/事件日志存盘，在隔离环境中通过代码路径重放。
6. **一次性 harness。** 启动系统的最小子集（一个服务，mock 依赖），用单个函数调用触发 bug 代码路径。
7. **属性/模糊回路。** 如果 bug 是"有时输出错误"，跑 1000 个随机输入寻找失败模式。
8. **二分 harness。** 如果 bug 出现在两个已知状态之间（commit、数据集、版本），自动化"在状态 X 启动、检查、重复"，从而可以用 `git bisect run`。
9. **差分回路。** 用相同输入同时跑旧版本和新版本（或两种配置），对比输出。
10. **HITL bash 脚本。** 最后手段。如果必须有人点鼠标，用 `scripts/hitl-loop.template.sh` 驱动 _他们_，让回路仍然结构化。捕获的输出反馈给你。

造出正确的反馈回路，bug 就修了 90%。

### 收紧回路

把回路当作产品。一旦你 _有_ 了一个回路，**收紧**它：

- 能更快吗？（缓存 setup、跳过无关初始化、缩小测试范围。）
- 能让信号更锐利吗？（断言具体症状，而非"没崩溃"。）
- 能让它更确定吗？（固定时间、种子 RNG、隔离文件系统、冻结网络。）

30 秒的抖动回路几乎等于没有回路；2 秒确定性的回路才是紧致的，是调试超能力。

### 非确定性 bug

目标不是干净复现，而是**提高复现率**。把触发器循环 100 次，并行化，加压力，缩小时间窗口，注入 sleep。50% 抖动的 bug 可调试；1% 的不行，所以持续提高复现率直到可调试。

### 当你确实无法构建回路时

停下来明确说明。列出你尝试过的方法。向用户请求：(a) 能复现的任意环境访问权限，(b) 脱敏的捕获产物（HAR 文件、日志 dump、core dump、带时间戳的屏幕录像），或 (c) 添加临时生产埋点的授权。**不要**在没有回路的情况下进入假设阶段。

### 完成标准：一个紧致的、能变红的回路

阶段一完成时，回路是**紧致**且**能变红**的：你能说出**一个命令**（脚本路径、测试调用、curl），你**已经至少跑过一次**（展示调用和输出，已脱敏），并且满足：

- [ ] **能变红**：它驱动了真实的 bug 代码路径，并断言**用户描述的确切症状**，因此能在这个 bug 上变红、修复后变绿。不是"跑完没报错"；它必须能 _捕获这个特定 bug_。
- [ ] **确定性**：每次运行结果一致（抖动 bug：按上文固定高复现率）。
- [ ] **快**：秒级，不是分钟级。
- [ ] **Agent 可运行**：你能无人值守运行；人在环中仅通过 `scripts/hitl-loop.template.sh`。

如果你发现自己在造出这个命令之前就开始读代码建理论，**停下来：直接跳到假设正是本 skill 要防止的失败模式。** 没有能变红的命令，就没有阶段二。

## 阶段二：复现并最小化

跑回路。看着它变红，bug 出现。

确认：

- [ ] 回路产生的是**用户**描述的失败模式，不是附近碰巧的另一个失败。错 bug = 错修复。
- [ ] 失败在多次运行中可复现（或对非确定性 bug，复现率高到足以调试）。
- [ ] 你已捕获确切症状（错误消息、错误输出、慢速计时），以便后续阶段验证修复确实解决了它。

### 最小化

一旦变红，把复现缩小到**仍能变红的最小场景**。每次只切掉一个输入、调用方、配置、数据、步骤，每次切完后重新跑回路，只保留对失败有承载力的元素。

为什么值得：最小化复现缩小了阶段三的假设空间（可怀疑的变量更少），并成为阶段五的干净回归测试。

完成标准：**每个剩余元素都有承载力**：去掉任意一个，回路就变绿。

在完成复现**且**最小化之前，不要进入下一阶段。

## 阶段三：提出假设

在测试任何假设之前，先生成**3 到 5 个排序假设**。只生成一个假设会锚定在第一个看似合理的想法上。

每个假设必须是**可证伪的**：陈述它做出的预测。

> 格式："如果 <X> 是原因，那么 <改变 Y> 会让 bug 消失 / <改变 Z> 会让它更糟。"

如果你无法陈述预测，这个假设就是感觉，不是假设：丢弃或打磨它。

**在测试之前把排序列表展示给用户。** 他们通常有领域知识能立刻重新排序（"我们刚部署了一个改动，正好是 #3"），或者知道哪些假设已经被排除了。成本低，收益大。不要阻塞，如果用户不在线，按你的排序继续进行。

## 阶段四：插桩

每次探测必须对应阶段三的一个具体预测。**一次只改一个变量。**

工具偏好：

1. **调试器 / REPL 检查**，如果环境支持。一个断点胜过十条日志。
2. **定向日志**，打在能区分假设的边界上。
3. 绝不"全量日志然后 grep"。

**给每条调试日志打唯一前缀标签**，如 `[DEBUG-a4f2]`。最后清理时一条 grep 搞定。无标签日志存活；有标签日志删除。

**性能分支。** 对性能回归，日志通常不适用。替代方案：建立基线测量（计时 harness、`performance.now()`、profiler、查询计划），然后二分。先测量，后修复。

## 阶段五：修复并加回归测试

**先写回归测试，再修**，但前提是存在一个**正确的接缝**。

正确接缝是指测试能在调用点以**真实 bug 模式**触发 bug。如果唯一可用的接缝太浅（bug 需要多个调用方才能触发，但测试只有单个调用方；单元测试无法复现触发 bug 的调用链），在那里加回归测试给出的其实是虚假信心。

**如果不存在正确接缝，这本身就是发现。** 记录下来。代码库架构正在阻止这个 bug 被锁定。在下一阶段标记这一点。

如果存在正确接缝：

1. 把最小化后的复现转化为该接缝处的失败测试。
2. 看着它失败。
3. 应用修复。
4. 看着它通过。
5. 重新跑阶段一的反馈回路，针对原始（未最小化）场景。

## 阶段六：清理

声明完成前必须：

- [ ] 原始复现不再复现（重新跑阶段一回路）
- [ ] 回归测试通过（或接缝缺失已记录）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（`grep` 前缀确认）
- [ ] 一次性原型已删除（或移到明确标注的调试位置）
- [ ] 被验证为正确的假设在 commit / PR 消息中陈述，让下一个调试者学到教训
