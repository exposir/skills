# 寻路（Wayfinder）

来了个模糊的大想法：一个 agent 会话装不下，从这到**目的地**的路也看不见。这种时候正确的动作是找路，不是闷头冲向目的地。本 skill 干的就是这件事：把路画成仓库 issue tracker 上的一张**共享地图**，然后一张一张地解决图上的**决策工单**——每张工单的产出是一个"决定"，不是一段要施工的代码——直到路线清晰。

目的地每次都不一样，**先给它起名字**，因为它决定了整张图怎么画。可能是要交接出去迭代的一份 spec、动工前必须锁定的一个决策、也可能是一次就地完成的变更（比如数据结构迁移）。地图本身不认领域：工程、课程内容，只要形状对得上都能用。

## 只画路，不赶路

Wayfinder 默认**只规划**：每张工单解决一个决策，图上没有悬而未决的东西了，地图就算画完。什么时候算画完？**当你开始手痒想直接干活的时候**——这通常就是到达地图边缘、该交接了的信号。某次努力想破例，可以在地图的 **Notes** 里写清楚，把执行也纳入地图；没写，就一律只产出决策，不产出交付物。

## 报名字，不报号

每张地图、每张工单都是一个 issue，都有**名字**（标题）。凡是给人看的内容（你的叙述、地图里的"已做出的决策"），一律用名字引用，绝不甩一串裸编号。`#42, #43, #44` 糊一脸谁也读不动；名字一眼能扫。id 和链接不会丢——它们藏在名字里头，跟着名字走，但永远不能代替名字。

## 地图

地图就是 tracker 上的一个 issue，打 `wayfinder:map` 标签，是这次努力的唯一正式产物。工单是它的子 issue。

地图是**索引，不是仓库**。它只列出"定了什么"，细节一律放在工单里，地图只写一行摘要加链接——一个决策只能住在一个地方。

**地图、子工单、阻塞关系、前沿查询具体落在哪，取决于用的是什么 tracker。** tracker 应该已经提供给你了；没有就让用户跑 `/setup-matt-pocock-skills`。怎么在这个仓库里表达这些操作，查 tracker 文档的"寻路操作"一节。没提供 tracker 时，默认用本地 markdown tracker。

### 地图正文长这样

整图的一张低分辨率快照，每个会话开头加载一次。**打开中的工单不列在图上**——它们是打开的子 issue，用查询找。

```markdown
## 目的地

<走到头是什么样子：这次努力要找到的那份 spec、那个决策或那个变更。一两行；每个会话选工单前先朝它看齐。>

## Notes

<领域；每个会话都该先看的 skill；这次努力的长期偏好>

## 已做出的决策

<!-- 索引：每条已关闭的工单一行，够判断相关性就行，细节点链接去工单里看 -->

- [<已关闭工单标题>](link)：<答案的一句话摘要>

## 尚未指定

<!-- 见"战争迷雾"：现在还开不成工单的在册迷雾；随前沿推进逐步"毕业" -->

<!-- 见"范围之外"：被明确判定不归这次努力管的工作；关掉，永不毕业 -->
```

### 工单

工单是地图的**子 issue**，tracker 给的 issue id 就是它的身份。正文只写问题，大小按**一个 100K token 的 agent 会话能装下**来切：

```markdown
## 问题

<这张工单要解决的决策或调查>
```

每张工单打一个 `wayfinder:<type>` 标签，`research`、`prototype`、`grilling`、`task` 四选一（见[工单类型](#工单类型)）。

**认领**：会话开工前先把自己指为工单负责人，然后才动手——这样并行跑的其他会话会自然跳过它。assignee 就是认领本身：一张开着又没负责人的工单，就是没人领。

**阻塞**用 tracker 原生的依赖关系，别自己发明。原因很实际：原生阻塞能在 tracker 自己的 UI 里把前沿画出来，人不用打开地图就知道哪张能拿。tracker 实在没有原生阻塞，才退化到在正文里写约定。阻塞某张工单的工单全部关闭，它就是**未阻塞**；所有"打开 + 未阻塞 + 未认领"的子工单合在一起，就是**前沿**——已知世界的边缘。

答案不写进工单正文，解决时另行记录（见[遍历地图](#遍历地图)）。过程中产出的东西（原型、文档）挂链接，不糊进工单。

## 工单类型

每张工单只有两种干活方式：**HITL**（人在场，和真人实时来回）或 **AFK**（agent 自己跑）。HITL 工单只能靠真人对谈解决，agent 绝不能替人答话——一个自问自答的拷问 agent，就已经违规了。

- **Research（AFK）**：读文档、啃第三方 API、翻本地知识库，把某个决策等着要的事实挖出来。起一个子代理，调 Skill 工具传 "research" 解决。需要当前工作目录之外的知识时用它。
- **Prototype（HITL）**：做个便宜、粗糙但具体的东西让人有反应对象——大纲、草稿、桩代码、UI/逻辑片段都行，调 Skill 工具传 "prototype"。产出物挂成工单资产。核心问题是"该长什么样 / 该怎么表现"时用它。
- **Grilling（HITL）**：对话，默认类型。永远调两次 Skill 工具："grilling" 和 "domain-modeling"。
- **Task（HITL 或 AFK）**：决策之前必须有人动手做掉的事——没啥可决定、可造、可研究的，但它不做完讨论就走不下去。比如先注册一个服务才有资格评它的 API、先开通权限、先把数据搬过来看形状。这是唯一"做事"而不是"做决定"的类型，它存在的理由只有一个：给某个决策解套，而不是交付目的地本身。agent 能自己跑就自己跑（AFK）；跑不了就给人一份精确到勾的清单（HITL）。事做完即解决，答案里记清做了什么、产出了哪些事实（凭证在哪、新 URL、数据行数）——后面的工单要靠这些。

## 战争迷雾

地图是**故意**画不全的：看不见的地方别硬画。活工单之外就是**战争迷雾**——你能感觉到有些决策和调查迟早要来，但现在钉不死，因为它们吊在还没解开的问号上。每解决一张工单，就照亮它前方的一片雾：雾里能说得清的东西升级成新工单，一次一张，直到通往目的地的路上没有雾、也没有剩工单。

地图的**尚未指定**区就是写这些朦胧预感的地方：疑似的问题、以后要回访的区域。它是朝向目的地、还没被发现的前沿——这里的东西都在范围内，只是还模糊到开不成工单。写得粗写得细都行，它顺便给协作者当路标。

**迷雾还是工单？** 判断标准只有一个：你现在能不能**把问题说准**——不是能不能答出来。

- 问题已经说得准，哪怕它被阻塞、暂时动不了 → **开工单**。
- 还说不那么准 → **进"尚未指定"**。别把雾提前切成工单大小：雾比工单粗，一片雾到时候可能毕业成好几张工单，也可能一张都不用。

**尚未指定**里不许放三样东西：已经定了的（在"已做出的决策"）、已经是活工单的、出了范围的（下一节）。

## 范围之外

雾只会聚在**朝向**目的地的方向。目的地定了，范围就定了：超出目的地的工作不是雾，是**范围之外**，它在地图上有自己的专区——你主动判断"不归这次管"的事。让它落在这里的是范围，不是清晰度。

范围之外的东西永不毕业（前沿到目的地为止）。它只可能以一种方式回来：目的地重画了，那是一次全新的努力，不是续跑。

划范围是一个定性动作，不是路上的一步。如果一张已经存在的工单被发现其实在目的地之外（画图时划错了，或被某个答案暴露出来）：**直接关掉它**（关掉的工单就明确离开前沿了），在**范围之外**留一行：一句话摘要 + 为什么出局，链到那张已关闭的工单。它不进**已做出的决策**——那里记的是实际走过的路，一条范围边界不算路。

## 调用

两种模式。不管哪种，**一个会话最多解决一张工单**——research 工单是唯一例外。

### 画地图

用户带着一个模糊想法来。

1. **给目的地起名。** 调两次 Skill 工具（"grilling" + "domain-modeling"），把这张地图到底要走到哪钉死：一份 spec、一个决策、还是一个变更。目的地定范围，所以最先做。
2. **画出前沿。** 再拷问一轮，这次**广度优先**：在整个问题空间上铺开扫，别在单条线上深挖，把悬着的决策和眼下能迈的第一步都翻出来。**如果这一扫根本没有雾**（路已经很清楚，全程一个会话就装得下），那就不需要地图——停下来，问用户想怎么继续。
3. **建地图**（打 `wayfinder:map` 标签）：目的地、Notes 填好，"已做出的决策"留空，雾草写进"尚未指定"。
4. **把现在说得准的工单建出来**，挂成地图的子 issue；**第二遍再连阻塞边**（issue 得先有 id 才能互相引用）。连完线，工单自然分成"前沿"和"被阻塞"两堆；暂时说不准的继续留在雾里（"尚未指定"区）。
5. **放出 research 子代理。** 刚建的每张 `research` 工单各起一个子代理（调 Skill 工具传 "research"），并行开跑，发现写进一次性的 `research/<name>` 分支，工单里留个上下文指针。
6. **收工。** 画图就是这一个会话的全部工作，它自己一张工单都不解决。

### 遍历地图

用户带着一张地图来（URL 或编号）。工单可给可不给：没给，你来挑下一个决策，别甩给用户挑。

1. 加载**地图**：那张低分辨率快照，别把每张工单正文都拉出来。
2. 选工单：用户指了就用他指的；没指就按顺序拿第一张前沿工单。**先认领**：把自己设成负责人，再开工。
3. 解决它。**按需放大**：相关或已关闭工单的正文要看再去取；`## Notes` 里点名的 skill 该调就调。拿不准就调两次 Skill 工具（"grilling" + "domain-modeling"）。
4. 记结论：答案发成一条**解决评论**，**关掉** issue，再往地图的"已做出的决策"追加一行**上下文指针**。
5. 维护地图：新浮出来的工单建出来再连线；被这个答案照清的雾升级成工单，并从"尚未指定"里划掉——它从此只以工单身份存在。如果答案暴露了某张工单（这张或别的）其实在目的地之外，**判它出局**，而不是顺手把它做掉。如果这个决策让图上别的部分作废，更新或删掉那些工单。

用户可能并行推进多张未阻塞工单，所以随时预期别的会话也在改这个 tracker。
