# 界面原型

在单个路由上生成**几个结构迥异的界面变体**，用悬浮底栏切换。用户在浏览器里来回翻，挑一个（或从每个里偷一点），然后把剩下的扔掉。

如果问题关乎逻辑/状态而不是长什么样，这是错误的分支。用 [LOGIC.zh.md](LOGIC.zh.md)。

## 什么情况下用这个形态

- "这个页面应该长什么样？"
- "定稿之前我想看看这个仪表盘的几个方案。"
- "试试设置页换个布局。"
- 任何用户本来会在脑子里三个模糊线稿之间纠结一整天的时刻。

## 两个子形态：强烈偏好子形态 A

界面原型在**贴着应用其余部分**时好判断得多：真实页头、真实侧栏、真实数据、真实密度。孤零零的一次性路由是真空：每个变体孤立地看都挺好。只要有合适的现成页面可以承载变体，就默认子形态 A。只有原型确实无处安放时才用子形态 B。

### 子形态 A：对现有页面做调整（首选）

路由已存在。变体渲染在**同一个路由**上，用 `?variant=` URL 查询参数切换。现有的数据获取、参数、鉴权全部保留。只有渲染部分换掉。这是默认选项；没有具体理由就选它。

如果原型对象还没有页面、但_天然该住在某个页面里_（仪表盘的新区块、设置页的新卡片、现有流程的新步骤），依然是子形态 A。把变体挂进宿主页面。

### 子形态 B：新页面（最后手段）

只有被原型的东西确实没有现成页面可住时才用（比如全新的顶层界面，或哪都嵌不进去的流程）。

**创建一条一次性路由**，沿用项目已有的路由约定。不要发明新的顶层结构。命名要一看就是原型（比如路径或文件名里带 `prototype`）。同样用 `?variant=` 模式。

选定子形态 B 之前先自查：真没有现成页面能嵌进去吗？空路由会藏起设计问题，而有人口的路由会暴露它们。

两种子形态的悬浮底栏完全一样。

## 流程

### 1. 写清问题并定 N

默认 **3 个变体**。超过 5 个就不再是"迥异"而是噪音，封顶在 5。

把计划写成一行，放在原型所在位置或文件顶部注释里：

> "设置页的三个变体，通过 `?variant=` 切换，在现有 `/settings` 路由上。"

无论用户在不在场反驳，这一行都有用。

### 2. 生成结构迥异的变体

起草每个变体。每个都要经得起：

- 页面的目的和它能拿到的数据。
- 项目的组件库 / 样式系统（TailwindCSS、shadcn、MUI、纯 CSS，什么都行）。
- 一个清晰的导出组件名，比如 `VariantA`、`VariantB`、`VariantC`。

变体必须**结构不同**：布局不同、信息层级不同、主要交互控件不同，不只是颜色不同。三张微调过的卡片网格不是界面原型，是壁纸。如果两个草稿出来太像，带着明确的"不许用卡片网格"重做其中一个。

### 3. 把它们接起来

在路由上建一个切换器组件：

```tsx
// 伪代码，按项目框架适配
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

子形态 A（现有页面）：现有数据获取全部留在切换器之上；每个变体只换渲染子树。

子形态 B（新页面）：`/prototype/<name>` 下的一次性路由挂同一个切换器。

### 4. 构建悬浮切换器

屏幕底部居中的一个小固定定位栏，三样东西：

- **左箭头**：切到上一个变体（循环）。
- **变体标签**：显示当前变体的键，如果变体导出了名字也一并显示，比如 `B (Sidebar layout)`。
- **右箭头**：切到下一个（循环）。

行为：

- 点箭头更新 URL 查询参数（用框架的路由器，如 Next 的 `router.replace`、React Router 的 `navigate` 等），这样变体可分享、刷新不丢。
- 键盘：`←` 和 `→` 方向键也能切。焦点在 `<input>`、`<textarea>` 或 `[contenteditable]` 里时不要拦截方向键。
- 视觉上与页面区分开（比如高对比度的胶囊形、轻微阴影），让它明显不是被评估的设计的一部分。
- 生产构建里隐藏：用 `process.env.NODE_ENV !== 'production'` 或等价检查来拦，防止原型误合并把底栏带给用户。

切换器放在单个共享组件里，两个子形态都能复用。放在项目里共享 UI 该在的位置。

### 5. 交接

给出 URL（和 `?variant=` 的键）。用户方便时会自己翻。有意思的反馈通常是**"我要 B 的页头加上 C 的侧栏"**，那才是他们真正想要的设计。

### 6. 存档答案并清理

某个变体胜出后，记下答案（哪个变体、为什么），然后按 [SKILL.zh.md](SKILL.zh.md) 描述的方式存档原型。把胜者合入真实代码，剩下的搬去一次性分支，不进主干：

- **子形态 A**：胜者合入现有页面；失败的变体和切换器从主干移除。
- **子形态 B**：胜出的变体升格为真实路由；一次性路由和切换器从主干移除。

完整变体集是一手来源，所以它进一次性分支，不进垃圾桶，因为留在主干上的变体组件和切换器会快速腐烂，还迷惑下一位读者。

## 反模式

- **只在颜色或文案上有差别的变体。** 那是微调，不是原型。真正的变体在结构上就意见相左。
- **变体之间共享太多代码。** 共享一个 `<Header>` 没问题；共享一个 `<Layout>` 就违背了初衷。每个变体都应该能自由抛弃布局。
- **把变体接上真实变更操作。** 只读原型没问题。如果变体需要改动数据，指向一个桩：问题是"这应该长什么样"，不是"后端好不好使"。
- **把原型直接升格上生产。** 变体代码是在原型约束下写的（没测试、错误处理最小化）。合入时正经重写。
