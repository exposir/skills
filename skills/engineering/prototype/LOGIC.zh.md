# 逻辑原型

一个自包含的单个 HTML 文件（一份**可分享的演示**），任何人都能通过点按钮来驱动一个状态模型。当问题关乎**业务逻辑、状态转移或数据形状**时用它：这类东西在纸面上看着合理，只有把它推过真实场景才会露出不对劲。

因为它是单文件、零安装，你可以把它交给非开发人员（设计师、PM、领域专家），让他们亲手感受模型。所以它要说人话，不说代码话。

## 什么情况下用这个形态

- "我不确定这个状态机处不处理得了先 X 后 Y 的边界情况。"
- "这个数据模型真的能表达……这种情况吗？"
- "我想在动手写之前先摸清 API 应该长什么样。"
- 任何想要**按按钮、看状态变化**的场景。

如果问题是"这应该长什么样"，这是错误的分支。用 [UI.zh.md](UI.zh.md)。

## 流程

### 1. 写清问题

写代码之前，先写下你在为哪个状态模型、哪个问题做原型。一段话，放在演示的顶部（放在可见的简介里，不只是注释）。回答错问题的逻辑原型纯属浪费，所以把问题写明白，方便事后核对，无论用户是现在在看还是离开后再回来看。

### 2. 把逻辑隔离进一个可移植的模块

把真正的逻辑（回答问题的部分）放进一个 `<script>` 块，写成一个小巧的纯模块，将来可以原样拎出来放进真实代码库。它外面的页面是一次性的；这个模块不是。

正确形态取决于问题：

- **纯 reducer**：`(state, action) => state`。动作是离散事件、状态是单个值时合适。
- **状态机**：显式的状态和转移。"现在哪些动作是合法的"属于问题的一部分时合适。
- **一组作用于简单数据类型的纯函数**。没有隐含的当前状态、只有变换时合适。
- **方法面清晰的类或模块**：逻辑确实持有持续的内部状态时合适。

选最适合所问问题的形态，_不是_最容易接到页面上的那个。保持纯粹：不碰 DOM，不碰 `document`，不让按钮处理器伸进来。页面调用它；任何东西都不能反向流动。这正是原型能在自身生命周期之后还有用的原因：问题一旦有答案，验证过的 reducer / 状态机 / 函数组就能独立搬进真实模块。

### 3. 构建可分享的 HTML 文件

一个文件，纯 HTML/CSS/JS：不用框架，不用打包器，不用服务器，全部内联，双击即开，经得起邮件转发。任何人打开它就能跑。

为非开发人员而写。每个标签都用**领域语言**，不是代码：按钮和状态读起来像业务本身，不像 reducer。用大白话解释正在发生什么。

自上而下排一个清晰的层次：

1. **标题和一句话说明**，讲清这个演示让你探索什么（第 1 步的问题）。
2. **当前状态**：完整相关状态，渲染成一个可读面板（带标签的字段，不是裸 JSON 堆），每次点击后重新渲染，让变化可见。在能帮非开发人员跟上的地方，点出刚才变的是什么。
3. **自由点击按钮**：每个动作一个按钮，随时可用，任何人都能按任意顺序摆弄模型。每次点击分发对应动作并重新渲染状态。
4. **引导演示**：一组**场景**，每个场景一个标签。每个标签里先是一段简短的平白描述（场景设置的情境和要观察什么），下面是该场景的**按顺序要点的按钮**。每一步都是真实按钮：点它执行那个动作并进入下一步。开始演示时重置到已知初始状态，保证场景每次跑法一致。

选那些能展示别扭场景的案例，就是纸面上难推演的那种：快乐路径、一个棘手的边界情况、一次本该非法的尝试。

保持美观但克制：干净的排版、宽松的间距、一种强调色。不要动画，不要花活：任何跟状态和按钮抢注意力的东西都不要。

### 4. 交接

把文件发给对方，或者直接帮对方打开。他们会在方便的时候点完演示和自由点击；有趣的时刻是当他们说"等等，这不应该可能啊"或"咦，我以为 X 会是另一种样子"；那些是_想法_里的 bug，这正是原型的全部意义。如果他们想要新动作或新场景，加上。原型会演化。

### 5. 存档答案和原型

原型答完它的问题后，先记下答案，再按 [SKILL.zh.md](SKILL.zh.md) 描述的方式存档原型。逻辑分支的对应关系：验证过的 reducer / 状态机 / 函数组搬进真实模块（决策被吸收）；HTML 外壳跟着进一次性分支，原型作为一手来源保存在那里，而且因为它是自包含单文件，在那个分支里依然双击就能重跑。

## 反模式

- **不要加测试。** 需要测试的原型就不再是原型了。
- **不要接真实数据库。** 用内存状态，除非问题就是关于持久化的。
- **不要泛化。** 不要"万一以后想支持 X 呢"。原型只回答一个问题。
- **不要把逻辑和页面混在一起。** 如果纯模块引用了 DOM、`document` 或按钮处理器，它就不再能拎走。让页面只是纯模块外面的一层薄壳。
- **不要上框架、打包器或服务器。** 一个收件人双击就开的文件；React 应用或 dev server 会毁掉"可分享"。
- **不要把 HTML 外壳送进生产。** 页面是为手工点击浏览优化的。它背后的逻辑模块才是值得留下的部分。
