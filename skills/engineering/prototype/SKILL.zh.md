# 原型

原型是**回答一个问题的一次性代码**。问题决定形态。

## 选分支

先确定要回答的是哪个问题：看用户的提示词、周边代码，或者用户在的话直接问：

- **"这个逻辑 / 状态模型对吗？"** → [LOGIC.zh.md](LOGIC.zh.md)。构建一个可分享的单个 HTML 文件（自由点击按钮 + 分标签的引导演示），把状态机推过那些在纸面上难以推演的场景，而且非开发人员也能操作。
- **"这个应该长什么样？"** → [UI.zh.md](UI.zh.md)。在单个路由上生成几个结构迥异的界面变体，通过 URL 查询参数和悬浮底栏切换。

两个分支产出的东西完全不同，选错了整个原型就白做了。如果问题确实含糊且用户不在，默认选与周边代码更匹配的分支（后端模块 → 逻辑；页面或组件 → 界面），并把假设写在原型顶部。

## 两个分支通用的规则

1. **从第一天起就是一次性的，并且明确标注。** 把原型代码放在它将来真正会被用到的地方附近（挨着它为之做原型的模块或页面），让上下文一目了然，但命名要让随便一个读者都看得出这是原型，不是生产代码。对于一次性界面路由，沿用项目已有的路由约定；不要发明新的顶层结构。
2. **启动要零门槛。** 界面原型用项目任务运行器里的一条命令启动：`pnpm <name>`、`python <path>`、`bun <path>` 等。逻辑演示是用户双击就开的单个 HTML 文件。两种都不需要动脑。
3. **默认不持久化。** 状态存在内存里。持久化正是原型要_验证_的东西，不是它应该依赖的东西。如果问题明确涉及数据库，用一个草稿库或本地文件，起个明确的"PROTOTYPE，用完就删"的名字。
4. **跳过打磨。** 不写测试，不做超出"能跑起来"的错误处理，不做抽象。目的是快速学到东西。
5. **把状态亮出来。** 每次动作之后（逻辑）或每次切换变体时（界面），打印或渲染完整的相关状态，让用户看到什么变了。
6. **完事就存档。** 把验证通过的决策合入真实代码，然后把原型本身作为**一手来源**存起来：提交到一个主干之外的一次性分支，并在实现 issue 上留下指向该分支的上下文指针。答案（结论和它解决的问题）也记在 issue 或 commit 里。主干只保留验证通过的决策。
