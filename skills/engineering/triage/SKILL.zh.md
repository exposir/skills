# 分类

把项目 issue tracker 上的 issue 推过一组小型的分类角色状态机。

如果本仓库把外部拉取请求也当作请求面（见 issue tracker 配置），分类同样覆盖它们：**一个 PR 就是一个附带了代码的 issue**，使用相同的角色、相同的状态、相同的状态机，只有下面标注"对于 PR"的几个差异。把裸 `#42` 按 tracker 配置解析为 issue 或 PR。

分类期间发布到 issue tracker 的每条评论或 issue **必须**以这个声明开头：

```
> *此内容由 AI 在分类过程中生成。*
```

- [AGENT-BRIEF.md](AGENT-BRIEF.md)：如何编写持久的 agent 简报
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)：`.out-of-scope/` 知识库的工作原理

## 角色

两个**类别**角色：

- `bug`：有东西坏了
- `enhancement`：新功能或改进

五个**状态**角色：

- `needs-triage`：维护者需要评估
- `needs-info`：等待报告者提供更多信息
- `ready-for-agent`：完全指定，可供离线 agent 接手
- `ready-for-human`：需要人工实现
- `wontfix`：不会处理

对于 PR，同样的状态对应附带的代码：`ready-for-agent` 表示附带了简报，agent 应该对 diff 进行下一步；`ready-for-human` 表示已准备好供人工合并。

每个分类过的 issue 应该恰好携带一个类别角色和一个状态角色。如果状态角色有冲突，标记出来并在做任何其他事情之前询问维护者。

这些是规范的角色名称。issue tracker 中实际使用的标签字符串可能不同。映射关系应该已经提供给你了。如果没有，让用户运行 `/setup-matt-pocock-skills`。

状态转移：一个未标记的 issue 通常先进入 `needs-triage`；从那里移到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。`needs-info` 在报告者回复后回到 `needs-triage`。维护者可以随时覆盖；标记看起来不寻常的转移，并在继续之前询问。

## 调用

维护者调用 `/triage` 并用自然语言描述他们想要什么。解读请求并执行。示例：

- "给我看所有需要我关注的东西"
- "我们看看 #42"（issue 或 PR）
- "把 #42 移到 ready-for-agent"
- "有哪些是 agent 可以捡的？"

## 显示需要关注的内容

查询 issue tracker 并呈现三个桶，最旧的在前：

1. **未标记**：从未分类。
2. **`needs-triage`**：评估进行中。
3. **`needs-info` 且自上次分类笔记以来有报告者活动**：需要重新评估。

当 PR 在范围内时，将外部 PR 纳入这些桶，每行标注 `[PR]` 或 `[issue]`。发现只暴露*外部* PR（tracker 配置定义了谁算外部），所以协作者进行中的 PR 不是分类工作。此过滤仅针对发现；显式命名的 PR 无论作者是谁都分类。

显示计数和每个条目的单行摘要。让维护者选择。

## 分类特定 issue 或 PR

1. **收集上下文。** 阅读完整 issue 或 PR（正文、评论、标签、作者、日期；对于 PR，还有 diff）。解析任何先前的分类笔记，以免重复询问已解决的问题。使用项目的领域术语表探索代码库，尊重所涉区域的 ADR。对代码库执行两项检查：(a) **冗余**：按领域概念搜索所请求行为是否已有实现（不只是请求的措辞），并报告你查找了哪里。如果找到，它就是一个已实现的 `wontfix`（步骤 5）。(b) **先前拒绝**：读取 `.out-of-scope/*.md` 并亮出任何与此请求相似的记录。

2. **推荐。** 告诉维护者你对类别和状态的推荐及理由，加上与请求相关的简要代码库摘要（包括是否已实现）。等待指示。

3. **验证主张。** 在任何拷问之前，检查主张是否成立。对于 bug，按报告者的步骤复现。对于 PR，确认 diff 做了它声称的事：检出，运行相关测试或命令。报告发生了什么：已确认（含代码路径）、失败，或细节不足（强烈的 `needs-info` 信号）。已确认的验证使 agent 简报强得多。

4. **拷问（如果需要）。** 如果请求需要充实，调用 Skill 工具两次，参数分别为 "grilling" 和 "domain-modeling"，一次一轮问题地把它拷问成形，在决策落地时内联打磨领域术语并更新 `CONTEXT.md`/ADR。

5. **应用结果：**
   - `ready-for-agent`：发布 agent 简报评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`：与 agent 简报相同的结构，但注明为什么不能委托（判断性决策、外部访问、设计决策、手动测试）。
   - `needs-info`：发布分类笔记（模板见下）。
   - 对于 `wontfix`，关闭 issue，评论取决于*原因*：
     - **已实现**：变更已经存在于代码库中。指出它在哪里；**不要**写入 `.out-of-scope/`（那个知识库是为*被拒绝*的请求准备的，不是已构建的）。
     - **被拒绝（bug）**：给出礼貌的解释，然后关闭。
     - **被拒绝（enhancement）**：写入 `.out-of-scope/`，在评论中链接它，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`：应用角色。如果有部分进展，可选择附加评论。

## 快速状态覆盖

如果维护者说"把 #42 移到 ready-for-agent"，信任他们并直接应用角色。确认你即将做什么（角色变更、评论、关闭），然后执行。跳过拷问。如果在没有拷问会话的情况下移动到 `ready-for-agent`，询问他们是否要写 agent 简报。

## Needs-info 模板

```markdown
## 分类笔记

**到目前为止我们已确定的内容：**

- 要点 1
- 要点 2

**我们还需要你提供的信息（@报告者）：**

- 问题 1
- 问题 2
```

在"已确定"下捕获拷问期间解决的所有内容，这样工作不会丢失。问题必须具体且可操作，不是"请提供更多信息"。

## 恢复之前的会话

如果 issue 或 PR 上存在先前的分类笔记，阅读它们，检查报告者是否已回答了任何未解决的问题，在继续之前呈现更新后的图景。不要重新询问已解决的问题。
