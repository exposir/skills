# 测试驱动开发

TDD 是红 → 绿的循环。本 skill 是让这个循环产出值得保留的测试的参考：什么是好测试、测试放哪里、反模式、以及循环的规则。每个章节在每个循环都适用：在循环之前和循环之中查阅它们，而不是循环之后。

探索代码库时，读一下 `CONTEXT.md`（如果存在），让测试名和接口词汇与项目的领域语言一致，并尊重你所触及区域的 ADR。

## 什么是好测试

测试通过公共接口验证行为，而不是实现细节。代码可以整个换掉，测试不该变。好测试读起来像规格说明："user can checkout with valid cart"（用户能用有效购物车结账）明确告诉你存在什么能力，而且它能在重构后存活，因为它不关心内部结构。

见 [tests.zh.md](tests.zh.md) 的示例和 [mocking.zh.md](mocking.zh.md) 的 mock 指南。

## 接缝：测试放哪里

**接缝**（seam）是你测试所在的公共边界：那个你能在不伸手进去的情况下观察行为的接口。测试住在接缝处，永远不针对内部。

**只在预先约定好的接缝处测试。** 写任何测试之前，先写下被测的接缝并与用户确认。没有确认过的接缝不写测试。你不可能什么都测，所以提前约定接缝，是让测试精力落在关键路径和复杂逻辑上，而不是每个边角情况上。

问一句："公共接口是什么，我们该测哪些接缝？"

当接口本身的形态存疑时（模块该多深、接缝该在哪、接口该暴露什么），用 Skill 工具调用 "codebase-design" 获取词汇。它是模块、接口、深度、接缝、适配器、杠杆、局部性这些术语的共同来源，是供查阅的参考，不是要跑一个会话。

## 反模式

- **与实现耦合**：mock 内部协作者、测试私有方法、或通过旁路验证（查数据库而不是用接口）。识别信号：重构时测试挂了，但行为没变。
- **同义反复**：断言用代码相同的方式重新计算期望值（`expect(add(a, b)).toBe(a + b)`、手工用同样方式推导快照、常量断言自己等于自己），所以它天然通过，永远不可能与代码意见相左。期望值必须来自独立的事实来源：一个已知正确的字面量、一个做过的例题、规格。
- **水平切片**：先写完所有测试，再写完所有实现。批量测试验证的是_想象中_的行为：你测的是事物的_形状_而不是面向用户的行为，测试对真实变化变得不敏感，而且你在理解实现之前就锁死了测试结构。改为**垂直切片**：一个测试 → 一个实现 → 重复，每个测试都是一颗**曳光弹**，回应上一个循环教给你的东西。

## 循环的规则

- **先红后绿。** 先写失败的测试，然后只写足够让它通过的代码。不要预支未来的测试或添加投机功能。
- **一次一片。** 每个循环一个接缝、一个测试、一个最小实现。
- **重构不属于循环。** 它属于审查阶段（见 `code-review` skill），不属于红 → 绿的实现循环。
