# 领域建模

在设计过程中主动构建和打磨项目的领域模型。这是一种*主动*的纪律：挑战术语、发明边界场景、在概念结晶的瞬间写下术语表和决策。（仅仅*读取* `CONTEXT.md` 中的词汇不算是这个 skill：那是任何 skill 都能做的一行习惯。这个 skill 是当你*改变*模型时用的，不仅仅是消费它。）

## 文件结构

大多数仓库只有一个上下文：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录存在 `CONTEXT-MAP.md`，说明仓库有多个上下文。这个映射文件指向每个上下文所在的位置：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 系统级决策
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← 上下文专属决策
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

惰性创建文件：只在有东西要写时才建。如果没有 `CONTEXT.md`，在第一个术语敲定时创建。如果没有 `docs/adr/`，在需要第一条 ADR 时创建。

## 会话过程中

### 用术语表来挑战

当用户使用的术语与 `CONTEXT.md` 中已有的语言冲突时，立即指出。"你的术语表把 'cancellation'（取消）定义为 X，但你似乎是在说 Y。到底是哪个？"

### 打磨模糊的语言

当用户使用模糊或过载的术语时，提出一个精确的规范术语。"你说 'account'（账户）：你指的是 Customer（客户）还是 User（用户）？这两者是不同的东西。"

### 讨论具体场景

当讨论领域关系时，用具体场景来压力测试。发明能探测边界情况的场景，迫使用户在概念边界上精确起来。

### 与代码交叉对照

当用户声称某件事是如何运作的，检查代码是否同意。如果发现矛盾，亮出来："你的代码取消的是整个 Order（订单），但你刚才说部分取消是可能的。哪个是对的？"

### 内联更新 CONTEXT.md

当术语敲定时，当场更新 `CONTEXT.md`。不要攒着批量处理：在它们发生时立即捕获。使用 [CONTEXT-FORMAT.zh.md](./CONTEXT-FORMAT.zh.md) 中的格式。

`CONTEXT.md` 应该完全没有实现细节。不要把 `CONTEXT.md` 当作规格、草稿本或实现决策的仓库。它就是术语表，仅此而已。

### 审慎地提供 ADR

只有当以下三个条件全部满足时才提议创建 ADR：

1. **难以逆转**：以后改变主意的成本有意义
2. **没有上下文会令人惊讶**：未来的读者会问"为什么他们这样做？"
3. **真实权衡的结果**：确实存在真正的替代方案，并且你出于特定原因选择了其中一个

如果三个条件中缺少任何一个，跳过 ADR。使用 [ADR-FORMAT.zh.md](./ADR-FORMAT.zh.md) 中的格式。
