# 代码审查

把 `HEAD` 和某个固定点之间的 diff，放到两条互不干扰的轨道上分别审查：

- **规范轴**：代码写得合不合这个仓库自己定的规矩？
- **规格轴**：改动做的是不是需求里要的那件事？

两条轨道各跑一个**并行子代理**，谁也别看谁的上下文，最后由本 skill 把两份结论摆在一起。

issue tracker 的位置应该已经提供给你了。如果 `docs/agents/issue-tracker.md` 不存在，让用户先跑 `/setup-matt-pocock-skills`。

## 怎么跑

### 第一步：钉死固定点

用户说的那个点就是固定点（commit SHA、分支名、tag、`main`、`HEAD~5`，都行）。没说就问。

先记下两条命令，后面两个子代理都要用：

- `git diff <fixed-point>...HEAD`（三点，对着 merge-base 比，不是直接比两个 tip）
- `git log <fixed-point>..HEAD --oneline`（这段距离里都有哪些 commit）

动手之前先验两件事：固定点解得出来（`git rev-parse <fixed-point>`），diff 不是空的。ref 写错了或者压根没有改动，要在这里就失败，别等两个子代理开起来才炸。

### 第二步：找需求来源

按这个顺序找这次改动背后的原始需求：

1. commit 消息里的 issue 引用（`#123`、`Closes #45`、GitLab `!67` 之类），按 `docs/agents/issue-tracker.md` 里的流程去取。
2. 用户调用时当参数传进来的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下跟分支名或功能对得上的规格文件。
4. 都找不到就问用户规格在哪。用户说没有，规格轴子代理就跳过，报告里写"无规格可用"。

### 第三步：找规范来源

仓库里所有教人怎么写代码的文档：`CODING_STANDARDS.md`、`CONTRIBUTING.md`，有什么算什么。

不管仓库自己写了多少，规范轴永远额外带一份**坏味道基线**：Fowler《重构》第 3 章里那组固定代码坏味道，仓库一个字没写也照样适用。两条规则压着它：

- **仓库说了算。** 仓库文档化的标准永远优先；它明确允许的写法，基线就不报。
- **永远是判断，不是判决。** 每条坏味道都是带标签的启发式（"疑似 Feature Envy"），不是硬性违规。和这里所有标准一样，工具链已经在查的东西就跳过。

每条坏味道都是"是什么 → 怎么改"两段式，对着 diff 逐条过：

- **神秘命名（Mysterious Name）**：函数、变量、类型的名字看不出它干什么、存什么。→ 改名；实在起不出像样的名字，说明设计本身就是糊的。
- **重复代码（Duplicated Code）**：同一个逻辑形状在改动里出现两处以上。→ 把共同的部分提出来，两边都调它。
- **依恋情结（Feature Envy）**：一个方法扒别人对象的数据，比扒自己的还勤。→ 把方法搬去它真正迷恋的数据旁边。
- **数据泥团（Data Clumps）**：几个字段或参数永远打包出现，分明是一个想出生的类型。→ 捆成一个类型，只传这一个。
- **基本类型偏执（Primitive Obsession）**：拿基本类型或字符串硬顶一个本该有自己的类型的领域概念。→ 给这个概念一个自己的小类型。
- **重复开关（Repeated Switches）**：对着同一类型，同样的 `switch`/`if` 级联在改动里翻来覆去。→ 换成多态，或者做一张两处共用的映射表。
- **霰弹式修改（Shotgun Surgery）**：一处逻辑变更，逼得 diff 里满处打补丁。→ 把一起变的东西归拢进一个模块。
- **发散式变化（Divergent Change）**：一个文件或模块为了好几个互不相干的理由被反复改。→ 拆开，让每个模块只为一个理由而变。
- **投机性通用（Speculative Generality）**：需求里压根没有，预先搭好的抽象、参数、钩子。→ 删掉，一路内联回去，等真需求冒头再说。
- **消息链（Message Chains）**：`a.b().c().d()` 一路点下去，调用方被迫背下整条链。→ 在链头对象上封一个方法，把整条路藏进去。
- **中间人（Middle Man）**：一个类或函数，活着的大部分意义就是转个手。→ 砍掉它，直接找正主。
- **拒绝继承（Refused Bequest）**：子类或实现者把继承来的东西大半扔掉或推翻。→ 别继承了，换组合。

### 第四步：并行开两个子代理

**规范轴子代理**的提示词里给三样东西：

- 完整的 diff 命令和 commit 列表。
- 第三步找到的规范来源文件清单，外加**第三步的坏味道基线全文**（必须整个贴进去，子代理没有别的渠道能看到它）。
- 任务："按文件 / hunk 汇报：(a) diff 里每一处违反文档化规范的地方，注明是哪份文件的哪条规则；(b) 你看到的每一条基线坏味道，点名并引用对应 hunk。违反文档化规范可以算硬违规，但基线坏味道一律是判断，而且仓库自己的规范压过基线。工具链已经在查的不用管。400 字以内。"

**规格轴子代理**的提示词里给：

- diff 命令和 commit 列表。
- 规格的路径或抓回来的内容。
- 任务："汇报：(a) 规格要求了但改动里缺失或只做了一半的；(b) 规格没要求、改动自己加的（范围蔓延）；(c) 看着做了、实现却不对的要求。每一条发现都引用规格原文。400 字以内。"

规格没有，规格轴就不开，最终报告里注明一句。

### 第五步：汇总

两份报告分别放在 `## Standards` 和 `## Spec` 标题下，原文或轻微整理后呈现。**不要**合并、不要重排，两个轴就是故意分开的（原因见下）。

收尾一句话：每个轴各几条发现，各轴内部最要命的是哪一条（如果有）。不要跨轴评总冠军，分轴就是为了防这种重排。

## 为什么要分两个轴

一个改动完全可能过一轴挂一轴：

- 规范条条都守，就是做的事不对 → **规范过、规格挂。**
- 需求做得一字不差，就是不合项目惯例 → **规格过、规范挂。**

分开汇报，一轴才盖不住另一轴。
