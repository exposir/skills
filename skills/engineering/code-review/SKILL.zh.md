对 `HEAD` 与用户给出的固定点之间的 diff 做双轴审查：

- **规范轴（Standards）**：代码是否符合本仓库文档化的编码规范？
- **规格轴（Spec）**：代码是否忠实实现了最初的 issue / 规格？

两个轴各自运行在**并行的子代理**里，互不污染上下文，最后由本 skill 汇总发现。

issue tracker 应该已经提供给你了。如果 `docs/agents/issue-tracker.md` 缺失，告诉用户运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 确定固定点

用户说的就是固定点（commit SHA、分支名、tag、`main`、`HEAD~5` 等）。如果用户没指定，问清楚。

把 diff 命令记一次：`git diff <fixed-point>...HEAD`（三点，与 merge-base 比较）。同时用 `git log <fixed-point>..HEAD --oneline` 记下 commit 列表。

继续之前，先确认固定点能解析（`git rev-parse <fixed-point>`）且 diff 非空。错误的 ref 或空 diff 应该在这里失败，而不是在两个并行子代理里失败。

### 2. 找规格来源

按顺序找最初的规格：

1. commit 消息里的 issue 引用（`#123`、`Closes #45`、GitLab `!67` 等），通过 `docs/agents/issue-tracker.md` 里的流程获取。
2. 用户作为参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能匹配的规格文件。
4. 都没有就向用户询问规格在哪。如果用户说没有，**Spec** 子代理跳过并汇报"没有可用规格"。

### 3. 找规范来源

仓库里任何说明代码该怎么写的文档，比如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

除了仓库自己的文档，规范轴永远带着下面的**坏味道基线**：一组固定的 Fowler 代码坏味道（《重构》第 3 章），即使仓库什么都没文档化也适用。有两条规则约束它：

- **仓库优先。** 仓库文档化的规范永远赢；如果它认可基线会标记的写法，就抑制那条坏味道。
- **永远是判断。** 每条坏味道都是一个带标签的启发式（"疑似 Feature Envy"），不是硬违规。和这里的任何规范一样，工具链已经强制检查的就跳过。

每条坏味道按"是什么 → 怎么修"来读，对照 diff 判断：

- **神秘命名（Mysterious Name）**：函数、变量或类型的名字看不出它做什么、装什么。→ 重命名；如果起不出诚实的名字，说明设计本身含糊。
- **重复代码（Duplicated Code）**：同一逻辑形状在改动的多个 hunk 或文件里出现。→ 提取共享形状，两处都调用它。
- **依恋情结（Feature Envy）**：一个方法访问别的对象的数据比访问自己的还多。→ 把方法移到它依恋的数据上。
- **数据泥团（Data Clumps）**：同样的几个字段或参数总是结伴出现（一个想诞生的类型）。→ 打包成一个类型，传这个类型。
- **基本类型偏执（Primitive Obsession）**：基本类型或字符串顶替了一个值得拥有自己类型的领域概念。→ 给这个概念一个自己的小类型。
- **重复开关（Repeated Switches）**：对同一类型的同一种 `switch`/`if` 级联在改动里反复出现。→ 用多态替代，或做一个两处共享的映射。
- **霰弹式修改（Shotgun Surgery）**：一个逻辑改动逼着在 diff 的很多文件里东改西改。→ 把一起变的东西收进一个模块。
- **发散式变化（Divergent Change）**：一个文件或模块因为好几个不相干的理由被改。→ 拆开，让每个模块只因为一个理由变化。
- **投机性通用（Speculative Generality）**：为规格里没有的需求加的抽象、参数或钩子。→ 删掉；回退内联，直到真实需求出现。
- **消息链（Message Chains）**：调用方不该依赖的长链 `a.b().c().d()` 导航。→ 在第一个对象上用一个方法把整条链藏起来。
- **中间人（Middle Man）**：一个类或函数大部分时间只是转发。→ 砍掉它，直接调真正的目标。
- **拒绝继承（Refused Bequest）**：子类或实现者忽略或覆盖了继承来的大部分东西。→ 放弃继承，改用组合。

### 4. 并行启动两个子代理

**Standards 子代理的 prompt** 应包含：

- 完整的 diff 命令和 commit 列表。
- 第 3 步找到的规范来源文件清单，**加上第 3 步的坏味道基线**（完整粘贴，子代理没有其他途径拿到它）。
- 任务简报："按相关文件 / hunk 汇报：(a) diff 违反文档化规范的每一处：引用规范（文件 + 规则）；(b) 你发现的任何基线坏味道：点名并引用 hunk。区分硬违规和判断：违反文档化规范可以是硬违规，但基线坏味道永远是判断，且仓库文档化的规范优先于基线。工具链已强制的跳过。400 字以内。"

**Spec 子代理的 prompt** 应包含：

- diff 命令和 commit 列表。
- 规格的路径或获取到的内容。
- 任务简报："汇报：(a) 规格要求了但缺失或不完整的部分；(b) diff 里规格没要求的行为（范围蔓延）；(c) 看起来实现了但实现不对的要求。每条发现引用规格原文。400 字以内。"

如果规格缺失，跳过 Spec 子代理并在最终报告里注明。

### 5. 汇总

把两份报告放在 `## Standards` 和 `## Spec` 两个标题下，原样或轻微整理呈现。**不要**合并或重排发现，因为两个轴是有意分开的（见"为什么是两个轴"）。

结尾用一句话总结：每个轴各有多少条发现，以及每个轴内部最严重的问题（如果有）。不要跨轴选出一个总冠军：这种重排正是分轴要防止的。

## 为什么是两个轴

一个改动可能过一个轴、挂另一个轴：

- 代码每条规范都遵守，但实现错了东西 → **规范过、规格挂。**
- 代码完全按 issue 的要求做，但破坏了项目惯例 → **规格过、规范挂。**

分开汇报，才能防止一个轴掩盖另一个轴。
