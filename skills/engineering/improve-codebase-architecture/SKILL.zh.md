# 改进代码库架构

浮现架构摩擦并提出**深化机会**：把浅模块变成深模块的重构。目标是可测试性和 AI 可导航性。

本命令_基于_项目的领域模型，并建立在共享的设计词汇上：

- 调用 Skill 工具参数为 "codebase-design" 获取架构词汇（**模块**、**接口**、**深度**、**接缝**、**适配器**、**杠杆**、**局部性**）及其原则（删除测试、"接口就是测试面"、"一个适配器 = 假设的接缝，两个 = 真实的"）。在每个建议中精确使用这些术语，不要滑向"组件"、"服务"、"API"或"边界"。
- `CONTEXT.md` 中的领域语言为好的接缝提供了名字；`docs/adr/` 中的 ADR 记录了本命令不应重新诉讼的决策。

## 流程

### 1. 探索

**先定范围再扫描：YAGNI。** 深化一个模块的价值在于让未来对它的变更更容易，所以对最近变更过的代码库部分给予额外权重。在你看之前先决定*在哪*看：

- 如果用户指定了方向（一个模块、一个子系统、一个痛点），用它，并跳过下面的推断。
- 否则，往回走一大段提交历史（`git log --oneline`），找到代码库的热点，那些反复出现的文件和区域，让这些路径先拉走你的注意力。如果变更分散，没有明确热点，扩大网。

先读项目的领域术语表（`CONTEXT.md`）和所涉区域的任何 ADR。

然后启动一个子代理来遍历代码库。不要遵循僵化的启发式；有机地探索，并注意你在哪里经历摩擦：

- 哪里理解一个概念需要在许多小模块之间跳来跳去？
- 哪些模块是**浅的**，接口几乎和实现一样复杂？
- 哪些纯函数只是为可测试性而提取出来，但真正的 bug 藏在它们被调用的方式里（没有**局部性**）？
- 哪些紧耦合的模块跨接缝泄漏？
- 代码库的哪些部分没有测试，或难以通过当前接口测试？

对你怀疑浅的任何东西应用**删除测试**：删除它会把复杂度集中起来，还是只是转移它？"是，集中"就是你要的信号。

### 2. 以 HTML 报告呈现候选

写一个自包含的 HTML 文件，放到操作系统临时目录，这样什么都不落进仓库。从 `$TMPDIR` 解析临时目录，回退到 `/tmp`（Windows 上用 `%TEMP%`），写到 `<tmpdir>/architecture-review-<timestamp>.html`，这样每次运行得到一个新文件。为用户打开它（Linux 上 `xdg-open <path>`，macOS 上 `open <path>`，Windows 上 `start <path>`），并告诉用户绝对路径。

报告使用**通过 CDN 加载的 Tailwind** 做布局和样式，以及**通过 CDN 加载的 Mermaid** 画图，用于关系以图/流/序列方式可靠传达结构的地方。混合使用 Mermaid 和手工 CSS/SVG 视觉：当关系是图状的（调用图、依赖、序列）用 Mermaid，当想要更编辑性的效果时用手工 div/SVG（质量图、横截面、折叠动画）。每个候选得到一个**前后对照可视化**。要视觉化。

对于每个候选，渲染一张卡片，包含：

- **文件**：涉及哪些文件/模块
- **问题**：为什么当前架构引起摩擦
- **解决方案**：纯英语描述会发生什么变化
- **收益**：用局部性和杠杆来解释，以及测试如何改进
- **前后对照图**：并排，手工绘制，展示浅度与深化
- **推荐强度**：`Strong`、`Worth exploring`、`Speculative` 之一，渲染为徽章

报告以**首要推荐**部分结尾：你会先解决哪个候选以及为什么。

**用 CONTEXT.md 的词汇讲领域，用 `/codebase-design` 的词汇讲架构。** 如果 `CONTEXT.md` 定义了 "Order"，就谈 "Order 入口模块"，不是 "FooBarHandler"，也不是 "Order 服务"。

**ADR 冲突**：如果一个候选与现有 ADR 矛盾，只有当摩擦足够真实，值得重新审视 ADR 时才亮出它。在卡片中清楚标记（比如一个警告标注："与 ADR-0007 矛盾，但值得重新打开，因为……"）。别列出 ADR 禁止的每个理论重构。

见 [HTML-REPORT.zh.md](HTML-REPORT.zh.md) 获取完整的 HTML 脚手架、图表模式和样式指南。

此时**不要**提出接口。文件写完后，问用户："你想探索哪一个？"

### 3. 拷问循环

用户选了一个候选后，调用 Skill 工具参数为 "grilling"，与他们一起走决策树：约束、依赖、深化模块的形状、接缝后面放什么、哪些测试能存活。

随着决策结晶，副作用内联发生；调用 Skill 工具参数为 "domain-modeling" 保持领域模型最新：

- **给深化模块起了 `CONTEXT.md` 中不存在的概念名字？** 把术语加进 `CONTEXT.md`。如果文件不存在，惰性创建。
- **在对话中打磨了一个模糊的术语？** 当场更新 `CONTEXT.md`。
- **用户以一个承重的理由拒绝了候选？** 提议 ADR，措辞为："要我把这个记录为 ADR 吗，这样未来的架构审视不会重新提出它？"只有当一个未来的探索者确实需要这个理由来避免重新提出时才提议；跳过短暂的理由（"现在不值得"）和自明的理由。
- **想探索深化模块的替代接口？** 调用 Skill 工具参数为 "codebase-design"，使用它的 design-it-twice 并行子代理模式。
