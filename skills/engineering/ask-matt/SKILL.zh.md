# Ask Matt

你不可能记住每个 skill，所以开口问。

一条**流程**（flow）是穿过多个 skill 的一条路径。大多数路径沿一条**主流程**走，两条**入口匝道**（on-ramp）并入其中。其余的都是独立 skill，或者是在底层运行的词汇层。

## 主流程：从想法到交付

大多数工作走的路线。你有一个想法，想把它做出来。

1. **`/grill-with-docs`** 通过访谈打磨想法。只要你在**工作目录里**，就从这里开始：它是有状态的，会把学到的东西记进 `CONTEXT.md` 和架构决策记录（Architecture Decision Record，简称 ADR）。（没有工作目录？改用 `/grill-me`，见"独立 skill"一节。两者运行的是同一个 `/grilling` 原语；`grill-with-docs` 会留下纸面记录，所以只要有仓库可以记录，它就是两者中更好的选择。）
2. **分支：所有问题都能在对话里敲定吗？** 如果某个问题需要可运行的答案（状态、业务逻辑、必须亲眼看到的界面），绕道做一个原型，去回两个方向都用 **`/handoff`** 衔接（原型住在自己的目录里，这正是 `/handoff` 的用途；见"阶段边界"）：
   - **`/handoff`** 转出去，然后针对那个文件开一个新会话，
   - **`/prototype`** 用一次性代码回答问题，
   - **`/handoff`** 把学到的东西转回来，并在最初的想法线程里引用它。
3. **分支：这是一次跨会话的构建吗？**
   - **是** → **`/to-spec`**（把线程变成规格），然后 **`/to-tickets`** 把它拆成 tracer-bullet 工单，每张工单声明自己的**阻塞边**。本地 tracker 上是 `.scratch/<feature>/issues/` 下一文件一单，手工按阻塞关系先做被依赖者；真实 tracker 上这些边变成原生阻塞链接，任何阻塞项已完成的工单都可以被领取：逐单启动 **`/implement`**，每单之间用 **`/clear`** 清空上下文。每张工单自包含，所以上一张的上下文用后即弃。
   - **否** → 就在当前上下文窗口里直接 **`/implement`**。

   无论哪条路，**`/implement`** 都是内部驱动 **`/tdd`**（一次一个红绿切片）构建每个 issue，最后在提交前运行 **`/code-review`**（标准 + 规格双轴审查）收尾。只想对某个具体行为做测试先行、不需要完整规格时，单独用 **`/tdd`**；想对照一个固定基准审查分支或 PR 时，单独用 **`/code-review`**。

### 上下文卫生

让第 1 到 3 步待在**同一个不间断的上下文窗口**里（在 `/to-tickets` 之前不要压缩或清空），这样访谈、规格、工单都建立在同一套思考上。之后每次 `/implement` 都从工单重新开始。

这一做法的上限是**[智慧区](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：在这个窗口内（当前最先进模型约 150k token）模型仍然能保持敏锐推理。如果会话在 `/to-tickets` 之前逼近上限，不要在降级状态下硬撑；在最近的阶段边界处 `/compact` 然后继续（见"阶段边界"）。

## 入口匝道

一种产生工作、然后并入主流程的起始情境。

- **bug 和请求堆积** → **`/triage`**。它把 issue 推过分类角色，产出"agent 就绪"的 issue，之后由 **`/implement`** 接手。

  分类只针对**不是你创建的** issue：bug 报告、进来的功能请求、任何原始到达的东西。`/to-tickets` 产出的工单已经 agent 就绪，**不要对它们再做分类**。

- **有东西坏了** → **`/diagnosing-bugs`**。对付难的那类：一眼看不出原因的 bug、间歇性抖动、在两个已知良好状态之间悄悄混进来的回归。它在拥有**紧致反馈回路**（一条已经会因为这个 bug 变红的命令）之前拒绝猜测，然后用回归测试修复。当真正的发现是"没有好的接缝把这个 bug 锁住"时，它的复盘交接给 **`/improve-codebase-architecture`**。

- **庞大而模糊的任务：绿地项目或大到单会话装不下的大功能** → **`/wayfinder`**，这里认知负担最重的流程。当从此处到目的地的路还看不见时，它在 issue tracker 上绘制一张由**决策工单**组成的**共享地图**，一次解决一张，产出**决策，而不是交付物**，直到迷雾退散、路径清晰。`/grill-with-docs` 打磨的是单会话能装下的想法，wayfinder 是给装不下的想法用的，它更慢、更重，所以只在那种场景用它，绝不要用在范围清晰的功能上。

  当地图清晰后，**它交接，不构建**：在 **`/to-spec`** 处并入主流程，把地图上的关联决策折叠成可构建的计划，然后照常 `/to-tickets`、`/implement`。把地图直接接进 `/implement` 会跳过折叠、丢掉关联细节，所以只有当真正确认任务很小时才直接走 `/implement`。

## 代码库健康

不是功能工作，只是维护。

- **`/improve-codebase-architecture`** 在你有空的时候运行，让代码库对 agent 保持宜居。它浮出**深化机会**；挑一个机会会_生成一个想法_，你可以带着它进入主流程的 `/grill-with-docs`。它是找到候选者的普查；**`/codebase-design`**（见下）是你设计选中的那个候选者的工作台。

## 底层的词汇层

两个模型可自动调用的参考 skill，运行在其他 skill 的*下方*，各自是其词汇的唯一事实来源。当问题出在**用词**而不是流程时，直接找它们；或者让上面的 skill 拉它们进来。

- **`/domain-modeling`**：打磨项目的*领域*语言：挑战一个模糊的术语，解决一个过载的词（"account"干三份活），把难以逆转的决策记成架构决策记录（ADR）。它是 `/grill-with-docs` 驱动的那门主动纪律，用来让 `CONTEXT.md` 保持一份干净的术语表。
- **`/codebase-design`** 是深度模块词汇（模块、接口、深度、接缝、适配器、杠杆、局部性），用来设计模块的*形状*：在干净接缝处用一个小接口承载大量行为。`/tdd` 和 `/improve-codebase-architecture` 都说这门语言。

## 阶段边界

一个**阶段**（phase）是会话内的一块工作：访谈、实现、QA。在两个阶段之间的**边界**处，你有五个选项，在它们之间做选择是整个地图里最模糊的决策：

- **继续**：留在原地。不花成本，不丢东西。
- **`/clear`**：清空窗口，当这里没有任何东西与下一步有关时。
- **`/handoff`** 写一个可移植的 markdown 文件。适用范围窄：只用于**新 harness**、**新目录**、**同事**，或**阶段中途**分叉一个子任务。它买到的是可移植性。
- **子代理**：把一个范围收得很紧的任务送进它自己的窗口，拿回一份报告。
- **`/compact`** 压缩当前上下文，用它开一个新会话。这是**默认项**，但应在决策树的底部，而不是第一反应。

读 [PHASE-BOUNDARIES.zh.md](PHASE-BOUNDARIES.zh.md) 看有序决策树：五个问题、每个分支背后的推理，以及为什么一手来源的成本使**继续**成为第一个该排除的选项。在**边界处**做决定；阶段中途要么继续，要么把剩下的拆给子代理。

## 独立 skill

完全脱离主流程。

- **`/grill-me`**：和 `/grill-with-docs` 一样不依不饶的访谈，但**无状态**：不在本地保存任何东西，不构建 `CONTEXT.md`。当你**不在工作目录里**（打磨计划、设计、一篇文字，任何下面没有仓库的东西）时用它。如果你在工作目录里，改用 `/grill-with-docs`：同样的访谈还留纸面记录，严格更优。
- **`/grilling`** 是访谈原语本身：轮次、前沿、事实是 agent 的活、决定是你的。`/grill-me` 和 `/grill-with-docs` 是两条具名入口，`/triage`、`/wayfinder`、`/improve-codebase-architecture` 内部都运行它。只有当你想要不带任何包装的访谈时，才直接找它。
- **`/resolving-merge-conflicts`** 逐块处理进行中的 merge 或 rebase 冲突，按追溯回双方一手来源的**意图**来解决，而不是挑行；然后完成操作。它从不运行 `--abort`。独立于所有流程：当你已经身处冲突之中时找它。
- **`/prototype`** 是一个小的、一次性程序，回答一个设计问题：这个状态模型顺不顺手，或者这个界面该长什么样。一次性是对代码写法的一种约束，不是销毁承诺：答案会折进真实代码，原型本身作为**一手来源**保存在主干分出的 `prototype/<name>` 分支上，由实现 issue 指向它。它是主流程第 2 步的绕道，但任何时候一个设计问题在纸面上难以敲定，都可以找它。
- **`/research`**：把阅读跑腿活交给一个**后台 agent**：它对照**一手来源**调查一个问题，然后在仓库里留下一份带引用的 Markdown 文件。它读的时候你继续干活。它产出的文件是要带*进*主流程 `/grill-with-docs` 的东西，因为调研喂养思考，而不是替代思考。
- **`/to-questionnaire`** 在堵住你的东西既不在你脑子里也不在代码库里、而在**别人脑子里**的时候出场，它写一份问卷给对方填。它是 `/grill-me` 的反面：不是就主题访谈你，而是就**发送**（发给谁、需要对方回什么）访谈你，把问题对准缺口。带回来的东西是 `/grill-with-docs` 或 `/to-spec` 的素材。
- **`/wizard`** 是给只有**人**能做的步骤用的：开通基础设施、配置凭证或 CI 密钥、在一个陌生的第三方控制台里点点点、跑一次性迁移或切换。它生成一个交互式 bash 脚本，打开每个 URL、捕获每个值、写进 `.env` 和 GitHub secrets，于是这个流程不再是你每次都要重新给 agent 解释一遍的事。模型可自动调用，所以 agent 一撞上只有你能过的墙就会用它。如果 agent 自己能做，它就该自己做；这个是给真正人在回路里的场景。
- **`/wait-what`** 是对没送达的消息的纠偏。对话中途、任何 skill 内部都能用，agent 会带着你缺掉的上下文、用平实的语言、借用 `CONTEXT.md` 的词汇，把它刚说过的话重新讲一遍。它是事后补救；`/grill-with-docs` 是事前预防，因为提前约定的共享语言才能让行话从一开始就不出现。
- **`/teach`**：跨多个会话学一个概念，把当前目录当作有状态的工作区。
- **`/writing-for-agents`** 是写 agent 消费的文档的参考：skill、AGENTS.md、被指向的文档。
